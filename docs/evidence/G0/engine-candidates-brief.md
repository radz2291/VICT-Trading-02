### 1.4 Determinism and backtest mechanics (claims in fetched docs)
- README/pyproject: "deterministic event-driven architecture"; "deterministic simulation" [`raw3/README-nautilus.md`, `raw3/pyproject-nautilus.toml`].
- **Bar timestamp / closed-bar timing**: "For execution simulation, each bar's initialization timestamp (`ts_init`) must represent the **close of the interval**. This prevents the complete bar from becoming visible before it formed" [`raw3/nt-doc-backtesting-bar-execution.md`; repeated in `raw3/nt-doc-concepts-bar.md`]. Open-timestamped bars need `ts_init = ts_event + interval_ns`.
- **Deterministic intrabar path**: bar volume split across four synthetic L1 updates (O/H/L/C); `bar_adaptive_high_low_ordering` picks a path and "The adaptive path is a **deterministic heuristic**, not a reconstruction of the actual trade sequence" [`raw3/nt-doc-backtesting-bar-execution.md`].
- **Look-ahead warning** (relevant to future-data isolation): "The engine does not provide a native next-bar-open fill mode... using the current bar's open from its `on_bar` callback would introduce look-ahead" [`raw3/nt-doc-backtesting-bar-execution.md`].
- **Deterministic matching / seeds**: historical book/trade data is treated as immutable; "A fixed fill-model `random_seed` makes that model's probabilistic decisions repeatable"; "This deterministic residual rule is separate from probabilistic fill-model slippage" [`raw3/nt-doc-backtesting-fill-prices-and-matching.md`]. Fill models expose `prob_slippage` etc. [`raw3/nt-doc-backtesting-fill-models.md`].
- **Bar/tick data handling**: data granularity ladder L3 book -> L2 -> L1 quotes -> trades -> bars; bars are the least granular and "require more simulation assumptions" [`raw3/nt-doc-backtesting-data-and-venues.md`]. Bars are converted to synthetic market updates for an L1 book; volume split across four points, remainder to close [`raw3/nt-doc-backtesting-bar-execution.md`]. Backtesting supports "historical quote tick, trade tick, bar, order book, and custom data with nanosecond resolution" [`raw3/README-nautilus.md`]. Bar model timestamps: `ts_event`/`ts_init` required [`raw3/nt-doc-concepts-bar.md`].
- **Gap behavior: not found in fetched docs.** Neither `raw3/nt-doc-backtesting-data-and-venues.md` nor `raw3/nt-doc-concepts-data.md` documents missing-interval behavior (only a `F_LAST` delta warning in the latter). **Unverified** - a G0/G3 proof must test it against our "missing interval is unavailable, never silently replaced" rule.
- **Pause/resume-like behavior**: streaming mode - "`run(streaming=True)` pauses when the current data is exhausted... Call `end()` after the final batch" [`raw3/nt-doc-backtesting-apis-and-runs.md`]; `add_data()` orders per-stream by replay timestamp and merges chronologically; `sort=True` default [`raw3/nt-doc-backtesting-apis-and-runs.md`].
- **Restart/reconstruction**: "optional Redis-backed state persistence" [`raw3/README-nautilus.md`]; live-side "Reconciliation: Startup and runtime checks align retained local state with venue reports" and a documented "Backtest and live differences" section (venue, transport, timing, persistence, external activity, reconciliation) [`raw3/nt-doc-live.md`].
- **Paper/live breadth**: "Live: Identical strategy implementations between research and live deployment" [`raw3/README-nautilus.md`]. Official adapters include Betfair, Binance, Bybit, Coinbase, Databento (data), Deribit, dYdX, Hyperliquid, **Interactive Brokers (Data/Execution)**, Kraken, OKX, Polymarket, Tardis (data), Architect AX, Blockchain, Derive, Lighter [`raw3/ADAPTERS-nautilus.md`]. Which adapters offer paper/testnet endpoints is **unverified** from fetched files.

## 4. What a minimal G0/G3 proof would need to demonstrate (per docs/ARCHITECTURE.md)

**NautilusTrader.** A minimal proof would run the pinned engine against the small dataset with known gaps and two contrasting rules: (i) **deterministic bar ordering** - verify `add_data`'s per-stream replay-timestamp sort and chronological merge produce identical run-to-run results twice, with a fixed fill-model `random_seed` and `bar_adaptive_high_low_ordering` fixed both ways; (ii) **closed-bar timing** - feed open-timestamped bars, set `ts_init = ts_event + interval_ns`, and assert `on_bar` fires only after the bar's four synthetic OHLC updates and that a prior-bar signal cannot touch the next bar's open (the documented look-ahead warning must be reproduced, not assumed); (iii) **spread/cost/fill** - bind a fee model (e.g. `MakerTakerFeeModel`) plus an L1 spread assumption on the SIM venue and record the actual fill rule used for market/limit/stop orders from the L1 residual-fill table; (iv) **human-paced step/pause/resume** - drive `run(streaming=True)` batch-by-batch with `clear_data()` between batches and prove state carries across pauses, then `end()`; (v) **future-data isolation** - with a multi-instrument multi-timeframe fixture, prove a strategy at time T cannot observe data timestamped after T (including the `time_bars_build_delay` aggregation boundary case); (vi) **restart/reconstruction** - kill mid-run and demonstrate reconstruction from persisted state (Redis-backed or catalog) plus, for the replay/live overlap story, the documented reconciliation path. Gap fixtures must directly test the undocumented missing-interval behavior, since that is the largest unverified area.

**LEAN.** A minimal proof would (i) pin the Docker image tag (`18132`/`latest` family) and run the two contrasting rules through `lean backtest` (or a direct `dotnet QuantConnect.Lean.Launcher.dll` run) with the same local dataset; (ii) **deterministic bar ordering** - since no determinism contract was found in fetched docs, run the identical backtest twice and hash result artifacts, plus test any randomness knobs (unverified what they are) for a fixed-seed path; (iii) **closed-bar timing** - verify how the engine slices bars/time and when `OnData` fires relative to bar close, from behavior because no fetched doc states the convention; (iv) **spread/cost/fill** - record the default fill/fee models (e.g. equity/fill models in `Engine`) as observed on the fixture, not from assumption; (v) **human-paced step/pause/resume** - determine whether LEAN offers any pause/step primitive at all in backtesting (none observed in fetched docs - likely needs a wrapper that slices data and restarts runs, which must be proven); (vi) **future-data isolation** - test LEAN's multi-timeframe warm-up/consolidator behavior for look-ahead at bar boundaries; (vii) **restart/reconstruction** - verify what state survives a mid-backtest interruption and whether results can be resumed or only re-run. The .NET 10 + Docker footprint must also be recorded against the app's deployment shape. The heavier footprint, stale GitHub release channel, and absence of fetched determinism/step-resume documentation make LEAN's proof surface larger than NautilusTrader's on current evidence.

**No engine is decided by this brief.** The above only maps what evidence exists and what the proof tasks would need to exercise.

## 6. Open risks for the G0 gate (engine side)

1. **License copyleft**: NautilusTrader is LGPL-3.0 (GPL family); LEAN is Apache-2.0. If the consumer app is not prepared to meet LGPL terms (dynamic linking, license notices, possible restructuring of the adapter boundary), that is a stop-condition-class license question for the owner before any engine decision.
2. **v2 vs v1 divergence**: NautilusTrader's stable line (1.231.0) and the Rust-native v2 line (rc5/rc6) have different Python APIs ("the latest stable v1 wheel, whose Python API differs from the v2 documentation"). A G0/G3 proof must pin which line it tests; proving v2 rc today risks re-proof when 2.0.0 stable lands.
3. **Undocumented gap semantics in both engines** could fail the pack's "unavailable, never silently replaced" rule; this is precisely what the pinned gap-fixture proof must falsify before either candidate passes.
4. **LEAN release-channel opacity** (no usable GitHub release since 2017; Docker numeric tags) makes provenance pinning and restart/reconstruction claims weaker than for NautilusTrader's versioned releases/wheels.
5. **Human-paced interaction** (step/pause/resume for human decisions) is first-class in NautilusTrader's streaming mode but unobserved in LEAN - a candidate-differentiating unknown to resolve by proof, not by prose.
6. All of the above were fetched from public sources on 2026-09-28; the transient 404s and the content-less quantconnect.com page are logged in `raw3/00-FETCH-MANIFEST.md` and should be re-verified by a fresh verifier session rather than trusted from this record.
